## 2. Options considered

| Option | Others may use/modify | Closed or hosted forks | Fit with open-core + paid Pro | Verdict |
|---|---|---|---|---|
| **AGPL-3.0** | yes | **Blocked**: derivatives and modified versions offered over a network must publish source under AGPL | Strong. Owner (sole licensor) can sell proprietary licences; many companies will not use AGPL, so they buy Pro | **Chosen** |
| GPL-3.0 | yes | Closed forks blocked, but a hosted (SaaS) fork need not publish source (no network clause) | Good, but the SaaS loophole matters if the product is ever hosted by others | Second choice |
| MPL-2.0 | yes | File-level copyleft only: others can combine with closed code and keep it private | Weak protection of the Community core | Not recommended |
| Apache-2.0 / MIT | yes | Anyone may take it private, sell it, compete with Pro | Weakest; no protection of the commercial moat | Not recommended |
| Source-available (PolyForm NC, BUSL) | limited | Blocked by terms | Strong, but not open source; discourages contributors | Not what the owner asked |

Rationale for AGPL: a desktop/CLI analyser is not itself a network service, so the "network" clause (section 13) matters
mainly if someone modifies QuietLoad and offers it as a web or hosted service; that is exactly the competitor scenario
the owner wants to stop. Strong copyleft also makes the code unattractive for proprietary competitors, who must either
publish their changes or buy a licence.

### "only" vs "or-later"
`AGPL-3.0-only` fixes the licence to version 3: you control what future versions of the AGPL cannot impose on your
code. `or-later` lets users adopt a later FSF version; useful for community compatibility but cedes control to a
third party. Because the owner is sole licensor and can relicense, "only" is the cautious choice. Compatibility note:
AGPL-3.0 and GPL-3.0 code can be combined (AGPL section 13 / GPL section 13); AGPL-3.0-only is NOT compatible with GPL-2.0-only
code. If Community contributors insist on GPL-3.0-or-later interoperability, the CLA still lets the owner relicense.

### What would change the decision
* Companies refusing AGPL block adoption and contributors disappear: consider GPL-3.0-only or MPL-2.0.
* The owner decides never to sell Pro / dual license: AGPL remains fine; CLA becomes optional (DCO suffices).
* The WebView2 native loader or runtime question (THIRD-PARTY-NOTICES section 7) turns out to conflict with AGPL
  conveying: change the shipping method.
* The CLA structure proves unworkable as drafted: change to a different structure
  (e.g. assignment of economic rights where permissible, or contributor-specific licences).

## 3. Dual licensing safely (open core)
1. **Own every line you relicense.** Merge outside code only under the CLA (or when it is Community-only, section 3.5).
   Keep a signed-CLA register (GitHub account, name, date, version, corporate entity).
2. **Code written by AI tools or employees/contractors**: confirm who owns it. Copyright in material generated by AI may be
   weak or absent depending on the jurisdiction (human authorship requirements) which is unsettled, which limits
   what you can license exclusively; contractors need written IP assignments; employer rights can attach (check your
   employment contracts).
3. **Do not copy code from the Pro repository into this one without a decision** (once published under AGPL it is AGPL
   for the recipients and cannot be recalled), and the reverse is fine only for code you own.
4. **No copyleft-only dependencies in Pro**: AGPL/GPL third-party code cannot be relicensed by you; keep all dependencies
   permissive.
5. DCO-only contributions (no CLA) are AGPL inbound=outbound: they cannot be used in Pro unless the contributor
   also grants rights; keep them Community-only or reject them.
6. Keep Pro, licence keys, private signing keys, Stripe secrets and activation servers out of this repository and its history.
7. The trade mark protects the brand, not the code (`TRADEMARK.md`).
8. Never describe Community as "free for commercial use without conditions": AGPL conditions apply.

## 5. AGPL compliance for the desktop/CLI app

**What triggers what.** Conveying a binary (AGPL sections 4-6) requires: the licence text, notices, and the Corresponding
Source (offered in writing or provided, for at least three years if using a written offer, or a network location
alongside the binary); section 13 requires modified versions that users interact with remotely over a network to
offer source. A local desktop app is not "remote" interaction, but offering the source link in the UI is the simplest
way to comply, and it satisfies the "Appropriate Legal Notices" duty of section 5(d): the interactive UI must show
copyright, no-warranty, that it is licensed under the AGPL, and how to view the licence.

**What must accompany every binary release (zip, installer, store package):**
1. `LICENSE` (AGPL-3.0), `NOTICE`, `THIRD-PARTY-NOTICES.md`, the .NET runtime's `THIRD-PARTY-NOTICES.TXT`.
2. A `SOURCE.txt` (or section in the README) with: the exact version/commit/tag, the source URL
   (`https://github.com/<owner>/<repo>/tree/<tag>` plus a release source archive), the offer: "The complete corresponding
   source code of this program is available at https://github.com/hannawissam/quietload-community-edition. If the link is unavailable, open an issue at https://github.com/hannawissam/quietload-community-edition/issues and we will send it
   on request for the cost of the medium for at least three years" and the build instructions (`dotnet build`,
   `publish.ps1`, SDK version, any required tools).
3. A reproducible build note (SDK version, RID) and checksums.
4. Attach the matching source archive to each GitHub Release (best practice; also keeps the source tied to the binary).
5. Keep copyright headers; modified files in forks must carry prominent change notices (AGPL section 5(a)).

## 6. Oracle-related points (unchanged in substance)
* **Trademarks:** the verbatim non-affiliation sentence everywhere (NOTICE, README, About, footer, website, store page).
  Oracle names are used descriptively only; never in the product name, logo, domain or executable. See `TRADEMARK.md`,
  `docs/trademark-and-naming.md`.
* **Documentation:** cite Oracle documentation by link and title only; no verbatim text; no Oracle scripts or My Oracle Support
  content. `Knowledge/*.cs` was sampled and reads as original; reword "Content follows the Oracle 19c Database Reference"
  comments; run a verbatim-match check. With a public repo, copied Oracle text is publicly visible.
* **Pack licensing:** AWR/ASH/ADDM need Oracle Diagnostics Pack; SQL Tuning Advisor/`DBMS_SQLTUNE` need Tuning Pack
  (see the "Database Licensing Information User Manual"). Keep per-snippet cautions; add the
  general notice to the SQL export header, Recommendations view, CLI output, README.
* **Sample reports:** the third-party Oracle sample reports (an oracle-base.com DB11G report and an Oracle EBS benchmark report)
  have no redistribution licence. The repository does not contain them: they were never committed and `EXAMPLES/` and
  `EXAMPLES-local/` are git-ignored. Tests that need them are skipped when absent; local runs use the git-ignored
  `EXAMPLES-local/` folder. Test fixtures in the repository are synthetic (invented names and data). A public repo AGPL
  licence does not license third-party files inside it, so never add such files.
* **Data and warranty:** AGPL sections 15-16 disclaim warranty and liability; add the plain "test before production"
  notice to the UI and SQL exports. Disclaimers have mandatory limits for consumers (France): not excluded: gross
  negligence, personal injury, legal guarantees, but a free-of-charge community release has a lighter exposure
  and the limits depend on the jurisdiction.
* **Export control:** no encryption features of its own; relies on Windows/.NET; classification is the exporter's call.
